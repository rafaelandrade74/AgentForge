Projeto

Desenvolvimento

AgentForge

Aplicação web auto-hospedada que orquestra o ciclo de desenvolvimento de um produto com agentes de IA. Você escreve uma demanda em linguagem natural e acompanha as tarefas até virarem um branch pronto para merge.

Papéis como agentes

Scrum Master, Dev, Tech Lead, Security e QA — cada um é uma execução do Claude Code em modo headless.

Isolado por tarefa

Cada tarefa roda num git worktree próprio, no branch agentforge/task-<id>.

Você no controle

Aprovações configuráveis. Nenhum agente faz push; o merge é seu.

Ao vivo e auditável

Prompt, saída, custo, duração e status de toda execução são guardados e transmitidos em tempo real.

Como funciona

Uma demanda passa por um fluxo de estados. As transições válidas ficam numa tabela no código (WorkflowDefinition).

Demanda→Scrum Master quebra em tarefas→Você aprova o plano→Dev implementa→Tech Lead + Security revisam→QA testa→Aguardando aprovação→Done
  • Revisão reprovada devolve a tarefa ao Dev com os apontamentos. No terceiro retorno ela vai para Bloqueada, esperando a sua decisão (Reexecutar ou Cancelar).
  • Dependências só liberam a tarefa quando estão em Done; tarefas dependentes nascem das branches das dependências.
  • Todo agente termina a saída com um bloco JSON validado. Saída inválida conta como falha e é reexecutada uma vez.
  • Todo agente roda pelo binário do CLI (nunca por API). O backend não lê nem guarda credenciais de agentes.

Escolher o cenário

A aplicação e o CLI do agente podem ficar em lugares diferentes. São três modos de execução, que se desdobram em cinco cenários de instalação:

CenárioModoQuando escolher
A. Docker completo2Caminho mais simples: tudo em containers, login do Claude pela interface
B. Docker com o seu Postgres2Já tem um Postgres e não quer outro banco no compose
C. Docker reaproveitando o login2O Claude já está logado no computador (Windows/Linux) e você não quer logar de novo
D. Docker + host agent1Quer usar o claude e o git do computador, com as credenciais deles
E. Tudo no computador3Não quer containers para a aplicação

Em dúvida? Comece pelo cenário A. Ele dá menos acoplamento com a sua máquina e não precisa de chave de API: só de uma conta Claude.

Instalação passo a passo

Escolha uma aba e siga só aquele cenário até o fim. Depois vá para Do primeiro projeto ao merge.

A. Docker completo (padrão)

Você terá db (Postgres), api (com claude e git na imagem) e web (interface) em containers. O login do Claude é feito pela interface e fica num volume.

Pré-requisitos

  • Docker com Compose v2.20+ (docker compose version). Docker Desktop no Windows/macOS; Docker Engine + plugin Compose no Linux.
  • Git para clonar o repositório.
  • Uma conta Claude. Não precisa de chave de API.
  • Portas livres: 8080 (interface) e 8081 (API, só em 127.0.0.1).

Passos

  1. Clone e entre na pasta: 
    git clone https://github.com/rafaelandrade74/AgentForge.git agentforge
cd agentforge
  2. Crie o .env com segredos aleatórios: 
    ./scripts/init-env.sh        # Linux/macOS
    ./scripts/init-env.ps1       # Windows (PowerShell)
    Alternativa: cp .env.example .env e troque ADMIN_PASSWORD, JWT_SECRET (mín. 32 caracteres) e POSTGRES_PASSWORD.
  3. Confirme que o .env tem a linha COMPOSE_PROFILES=local-db (é ela que sobe o Postgres do compose).
  4. Suba tudo (a primeira vez compila as imagens e leva alguns minutos): 
    docker compose up -d --build
  5. Verifique: docker compose ps. db, api e web devem estar healthy. As migrations rodam sozinhas.
  6. Abra http://localhost:8080 e entre com ADMIN_USERNAME / ADMIN_PASSWORD do .env (usuário padrão admin).
  7. Abra Agentes. Se o Claude Code estiver Conectado, pronto. Se estiver Não conectado, clique em Conectar, abra o link, entre na sua conta e cole o código de volta na tela. O login fica no volume claude-config.
  8. Clique em Testar. É uma chamada mínima e consome um pouco de crédito.
Se algo der errado
SintomaSolução
Compose reclama de ADMIN_PASSWORD/JWT_SECRETO .env não existe ou está incompleto: refaça o passo 2
api não fica saudável (senha do banco)Você trocou POSTGRES_PASSWORD após o primeiro start: docker compose down -v (apaga os dados) e suba de novo

B. Docker com o seu Postgres

Igual ao cenário A, mas sem o container db: a API usa um Postgres que você já mantém.

Pré-requisitos

Os do cenário A, mais um Postgres 14+ acessível a partir do container da API.

Passos

  1. Faça os passos 1 e 2 do cenário A (clone e .env).
  2. No seu Postgres, crie banco e usuário vazios: 
    CREATE USER agentforge WITH PASSWORD 'uma-senha-forte';
CREATE DATABASE agentforge OWNER agentforge;
  3. Edite o .env: 
    COMPOSE_PROFILES=
DATABASE_URL=Host=meu-postgres;Port=5432;Database=agentforge;Username=agentforge;Password=uma-senha-forte
    • COMPOSE_PROFILES= vazio impede o db do compose de subir.
    • Postgres no próprio computador: use Host=host.docker.internal (e permita conexões que não sejam só de 127.0.0.1: listen_addresses e pg_hba.conf).
    • Postgres em outro container: ponha os dois na mesma rede Docker e use o nome do container em Host=.
  4. Suba: docker compose up -d --build. docker compose ps deve mostrar só api e web.
  5. Siga os passos 6 a 8 do cenário A (entrar, conectar o Claude, testar).
Se algo der errado
SintomaSolução
api reinicia em loopdocker compose logs api. Quase sempre é a DATABASE_URL ou o firewall/pg_hba.conf
"database does not exist"O banco precisa existir antes; as migrations criam só as tabelas
O db do compose subiu mesmo assimCOMPOSE_PROFILES não está vazio (no .env ou exportado no terminal)

C. Docker reaproveitando o login do Claude do computador

O cenário A, mas o Claude dentro do container usa o login que já existe no seu computador.

No macOS não funciona: o login fica no Keychain. Use o cenário A. Vale só para Windows e Linux, onde existe ~/.claude/.credentials.json.

Passos

  1. Confirme que o arquivo de login existe: 
    Test-Path "$env:USERPROFILE\.claude\.credentials.json"   # Windows: True
    ls ~/.claude/.credentials.json                           # Linux
  2. Faça os passos 1 e 2 do cenário A.
  3. No .env, aponte para a pasta (use / mesmo no Windows): 
    CLAUDE_CONFIG_SOURCE=C:/Users/voce/.claude      # Linux: /home/voce/.claude
  4. No Linux o container roda com UID 1654: a pasta precisa ser gravável por ele (ex.: setfacl -R -m u:1654:rwX ~/.claude).
  5. docker compose up -d --build e siga os passos 5 a 8 do cenário A. Em Agentes, o Claude já aparece Conectado.

O Claude do container passa a ler e gravar nessa pasta (inclusive a renovação do token) e a obedecer as configurações dela (hooks, plugins). Se isso incomoda, use o cenário D ou o login pela tela (A).

D. Docker + claude e git do computador (host agent)

api e web ficam em containers, mas todo claude e git roda no seu computador, por um pequeno serviço (o host agent), usando o binário, o login e as credenciais Git que você já tem.

Pré-requisitos

  • Os do cenário A (Docker + Compose).
  • No computador: .NET SDK 8+, git e claude no PATH, com o Claude já logado: 
    dotnet --version
git --version
claude --version
    Se não estiver logado, rode claude uma vez e faça /login.
  • Porta 8787 livre em 127.0.0.1.

Passos

  1. Faça os passos 1 e 2 do cenário A (clone e .env).
  2. Terminal 1 — inicie o host agent e deixe aberto: 
    ./scripts/host-agent.ps1        # Windows
    ./scripts/host-agent.sh         # Linux/macOS
    Na primeira vez o script cria HOST_AGENT_TOKEN e HOST_WORKSPACES_ROOT no .env. HOST_WORKSPACES_ROOT é a pasta do computador onde ficam clones e worktrees (padrão .agentforge/repos). Outra pasta: ./scripts/host-agent.ps1 -Root D:/agentforge/repos.
  3. Terminal 2 — suba a aplicação com os dois arquivos do compose: 
    docker compose -f docker-compose.yml -f docker-compose.host-agent.yml up -d --build
  4. Abra http://localhost:8080 e entre. Em Agentes, o Claude aparece como CLI no seu computador e Conectado. Clique em Testar.
  5. A URL do repositório e os caminhos de um projeto são os do computador. A tela Git avisa que o git é o do computador e não oferece gerar chave.

Linux com Docker nativo

O container não alcança o 127.0.0.1 do host. Inicie o host agent em todas as interfaces e restrinja a porta 8787 por firewall:

./scripts/host-agent.sh "" http://0.0.0.0:8787

SintomaSolução
Erro de conexão com o host agentO terminal 1 não está rodando, ou a porta/URL não bate com HOST_AGENT_URL

E. Tudo no computador, sem Docker para a aplicação

A API roda nativa (e serve a própria interface), usando o dotnet, git e claude do computador. Só o Postgres pode ficar num container.

Pré-requisitos

  • .NET SDK 8+, Node 20+, git e claude no PATH, com o Claude já logado.
  • Um PostgreSQL existente, ou Docker apenas para o script subir um.
  • Porta 8080 livre (ou escolha outra com -Urls).

Passos

  1. Clone o repositório e crie o .env (passos 1 e 2 do cenário A) antes de rodar o script, para não ficar com os valores de exemplo.
  2. Suba, escolhendo uma opção de banco:

    Sem Postgres instalado (o script sobe o container agentforge-native-db em 127.0.0.1:5432):

    ./scripts/run-native.ps1 -StartPostgres        # Windows
    ./scripts/run-native.sh --start-postgres       # Linux/macOS

    Com um Postgres seu: crie banco e usuário vazios, ponha no .env NATIVE_DB_CONNECTION=Host=localhost;Port=5432;Database=agentforge;Username=...;Password=... e rode o script sem a opção de banco.

  3. Na primeira vez o script compila a interface (npm ci + ng build). Para recompilar: -Rebuild (--rebuild no .sh). No .ps1: outra porta com -Urls http://localhost:9090 e outra pasta de clones com -Workspaces D:/repos.
  4. Abra http://localhost:8080, entre e vá em Agentes: o Claude deve aparecer Conectado (login do computador). Clique em Testar.

Clones ficam em .agentforge/repos. A chave SSH gerada pelo AgentForge fica em ~/.agentforge/ssh, nunca no seu ~/.ssh. Para parar: Ctrl+C; o banco continua de pé (docker stop agentforge-native-db).

SintomaSolução
"'dotnet' não está no PATH" (ou node/git)Instale e abra um terminal novo

Do primeiro projeto ao merge

Vale para qualquer cenário.

  1. Agentes: confira que o Claude Code está Conectado e que o Testar passou.
  2. Cadastre um projeto por um dos caminhos:
    • Importar do GitHub (o mais simples): Projetos → Importar do GitHub. Cole um token pessoal (escopo repo), clique em Listar meus repositórios, escolha um e Importar e clonar. Repositório público dispensa o token: digite dono/nome.
    • Projeto de exemplo (cenários A/B/C): docker compose exec api sh /examples/make-sample-repo.sh cria /data/repos/_sample/tasks-api.git; use essa URL em Projetos → Novo projeto.
    • Manual: Projetos → Novo projeto com nome, URL do repositório, branch base e (opcional) comandos de build e teste.
  3. Nova demanda → Criar e iniciar refinamento. Descreva em linguagem natural o que quer. O Scrum Master lê o repositório e propõe as tarefas.
  4. Aprovar plano na tela da demanda. O quadro do projeto mostra as tarefas andando; clique numa tarefa para ver o log ao vivo, o diff e as execuções.
  5. Em Aguardando aprovação, revise o diff e aprove ou rejeite com comentário (a tarefa volta ao Dev). Tarefas que voltam três vezes ficam Bloqueadas.
  6. Depois de Done, o trabalho está no branch agentforge/task-<id> do clone local. Nenhum agente faz push: o merge é seu.

Onde ficam os arquivos: clones em <raiz>/<id-do-projeto>/repo e worktrees em <raiz>/<id-do-projeto>/worktrees/<id-da-tarefa>, com a raiz em /data/repos (volume repos; A, B, C), HOST_WORKSPACES_ROOT (D) ou .agentforge/repos (E).

Modo automático: marque o projeto como automático para dispensar as duas aprovações humanas. Use só em projetos de teste. O agente de cada papel é escolhido em Agentes e os prompts, em Prompts.

Repositórios privados

Chave SSH pela interface

  1. Abra Git e clique em Gerar chave SSH. Copie a chave pública: a privada (ed25519, volume git-ssh) nunca sai do servidor.
  2. No GitHub, no repositório: Settings → Deploy keys → Add deploy key. Cole a chave e deixe "Allow write access" desmarcado. Para vários repositórios, use Settings → SSH and GPG keys da conta.
  3. De volta em Git, use Testar acesso com a URL SSH (git@github.com:org/repo.git).
  4. Cadastre o projeto com essa URL SSH.

"Gerar outra" substitui a chave (a antiga deixa de valer); "Remover" apaga. Ao importar do GitHub, o token é usado só naquela chamada: não é guardado nem registrado em log, e a chave é registrada como deploy key somente leitura.

Controlar pelo Claude Code (MCP)

O AgentForge é também um servidor MCP (HTTP, POST /mcp). O Claude Code, ou qualquer cliente MCP, pode criar projetos e demandas, acompanhar tarefas, ler o diff e aprovar ou rejeitar entregas por conversa. Funciona em todos os cenários.

  1. Abra Integração na interface e crie um token de acesso (afk_...). O valor aparece uma única vez; vale só no /mcp, é guardado como hash e pode ser revogado ali.
  2. Registre o servidor (a tela já gera o comando com seu token e endereço): 
    claude mcp add --transport http agentforge http://localhost:8080/mcp --header "Authorization: Bearer afk_..."
    Para outros clientes, em .mcp.json: 
    {"mcpServers":{"agentforge":{"type":"http","url":"http://localhost:8080/mcp","headers":{"Authorization":"Bearer afk_..."}}}}
  3. Converse: "crie uma demanda no projeto X para adicionar o filtro por status e inicie", "o que depende de mim?", "mostre o diff da tarefa e aprove".
As 18 ferramentas

list_projects, get_project, create_project, create_demand, start_demand, approve_plan, get_demand, list_tasks, get_task, get_task_diff, get_run_output, approve_task, reject_task, retry_task, cancel_task, list_pending_actions, list_agents, test_agent.

As de leitura são marcadas como somente leitura e cancel_task como destrutiva. Não existe ferramenta que faça push, merge ou apague projeto. start_demand, create_demand com start e test_agent gastam créditos.

Atrás de um proxy reverso, repasse /mcp à API e use HTTPS: o token trafega no cabeçalho.

Atrás de um proxy reverso

O web (Nginx) já repassa /api, /hubs (SignalR/WebSocket) e /swagger para a API. Aponte o seu proxy para web:8080 e habilite WebSocket em /hubs/:

server {
    server_name agentforge.exemplo.local;
    location / {
        proxy_pass http://127.0.0.1:8080;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_read_timeout 1h;
    }
}

Use HTTPS no proxy: o login e o token trafegam por ele.

Backup e atualização

Volumes nomeados: pgdata (banco), repos (clones e worktrees) e claude-config (login).

# backup do banco
docker compose exec -T db pg_dump -U agentforge agentforge > backup.sql
# restaurar (banco vazio)
docker compose exec -T db psql -U agentforge agentforge < backup.sql

# atualizar o AgentForge (cenário D: com os dois -f)
git pull && docker compose up -d --build
  • As migrations aplicam sozinhas no start. Faça backup antes de atualizar ambientes com dados que importam.
  • Atualizar o Claude do container: mude CLAUDE_CODE_VERSION no .env e rode docker compose up -d --build api.
  • Mais tarefas ao mesmo tempo: ORCHESTRATOR_CONCURRENCY=2 (ou mais).
  • docker compose down mantém os dados; docker compose down -v apaga banco, clones e login.

Segurança

  • db, api e web rodam sem root (API com UID 1654, front com nginx-unprivileged), com no-new-privileges e cap_drop: ALL; o front tem sistema de arquivos somente leitura.
  • Só o web é publicado na rede; o Postgres não é exposto.
  • Nenhum agente faz push, e o backend não guarda credenciais de agentes.

No cenário de container, os agentes executam comandos (build, testes) dentro do container da API; nos cenários D e E, no seu computador, dentro do worktree da tarefa. Rode o AgentForge com repositórios em que você confia.
